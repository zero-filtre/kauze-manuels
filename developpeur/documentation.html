    La documentation elle-même¶

    Les trois manuels vivent dans docs/manuel/, une page Markdown par sujet. Ils sont lus à quatre endroits : dans l'application, par le chatbot, par un site local de relecture, et en ligne, les trois manuels.

    L'en-tête d'une page¶

    ---
title: Le verrou de visibilité
audience: utilisateur
sources:
  - backend/.../VisibilityLockService.java
---

    L'audience vient de l'en-tête, jamais du dossier : une page mal rangée se voit au lieu de disparaître silencieusement. Les sources listent le code que la page décrit, et c'est ce qui rend la dérive détectable. Un test échoue si une page n'a pas de titre, pas de source, une source inexistante, ou une audience qui ne correspond pas à son dossier.

    Ce qui part chez le client, et ce qui reste¶

    Les manuels utilisateur et administrateur sont copiés dans le jar au moment du build, par la section resources du fichier Maven, qui les lit depuis ../docs/manuel. Le manuel développeur n'y est pas : il est lu depuis le dépôt, par le chemin docs.developer-dir, vidé dans la configuration de production.

    Conséquence sur la construction de l'image : le contexte Docker du backend est la racine du dépôt et non backend/, sinon ../docs/manuel n'existe pas dans le conteneur de build. Maven ignore un répertoire de ressources absent sans rien dire, donc le jar sortirait sans documentation et sans index de recherche, sans qu'aucune étape n'échoue. Trois assertions de BundledManualDeliveryTest gardent le Dockerfile et le contexte, parce qu'aucun test lancé par Maven ne peut voir le problème : sur un poste de développement, ../docs/manuel est toujours là. Au démarrage, un manuel vide est signalé par un avertissement.

    Deux verrous indépendants, donc : les fichiers ne sont pas dans l'image, et docs.developer-enabled est faux en production. Un administrateur qui redéploierait avec un autre profil ne ferait pas apparaître un manuel qui n'existe pas sur son disque.

    Le périmètre de lecture est décidé une seule fois, côté serveur : soignant, manuel utilisateur ; administrateur, plus le manuel administrateur ; administrateur hors production, tout. La même règle filtre la lecture et la recherche, elles ne peuvent pas diverger.

    Le découpage¶

    Une page est découpée par section de second niveau, chaque extrait gardant l'ancre de son titre. C'est ce qui permet à une citation d'ouvrir la page au bon endroit ; le client recalcule la même ancre que le serveur. Une section trop longue est coupée aux paragraphes sans perdre son ancre, et un titre écrit à l'intérieur d'un bloc de code n'ouvre pas de section.

    L'ancre est celle de python-markdown, donc celle de MkDocs : accents repliés, ponctuation retirée et non changée en tiret. Les manuels étant rendus par deux moteurs, un lien vers l'ancre d'une autre page doit atterrir au bon endroit dans les deux, et scripts/docs/test_ancres.py refuse toute ancre morte. L'empreinte du corpus inclut l'ancre, donc un changement de cette règle reconstruit l'index vectoriel au démarrage suivant, sans geste manuel.

    La recherche vectorielle¶

    Chaque extrait est embarqué au démarrage par le modèle multilingue déjà chargé par l'application, avec le titre de sa page et celui de sa section : aucun modèle supplémentaire n'est téléchargé. La question est embarquée à la volée et la proximité se mesure par cosinus. Les préfixes passage: et query: attendus par la famille e5 vivent dans un seul endroit, l'embedder, pour qu'un extrait indexé et une question posée soient traités pareil.

    La construction se fait hors du démarrage, sur un fil dédié : elle dure une trentaine de secondes sur le corpus actuel, et ni les requêtes ni les autres tâches de démarrage n'ont à l'attendre. L'index est ensuite persisté avec l'empreinte du corpus, si bien qu'un redémarrage sur une documentation inchangée le recharge instantanément. Tant qu'il n'est pas prêt, ou si le modèle est indisponible, la recherche retombe sur le lexical sans rien casser.

    Le seuil docs.embedding.min-similarity écarte les extraits trop éloignés. C'est le réglage à tourner si les réponses deviennent bruyantes ou au contraire trop rares : les modèles e5 compriment les scores, d'où une valeur par défaut élevée.

    La fusion avec le lexical¶

    Le lexical n'a pas disparu : pondération par rareté du terme, titres comptant double, accents et casse ignorés. Il reste imbattable sur les termes exacts du produit, un nom d'écran, une unité, un nom de modèle. Les deux classements sont fusionnés par rang réciproque, ce qui évite de comparer des scores hétérogènes : un extrait bien placé dans l'une des listes remonte, un extrait présent dans les deux passe devant.

    La réponse¶

    Les extraits retrouvés sont passés au modèle de langue configuré, avec le prompt prompts/docs-chat.md qui lui interdit de sortir de ces extraits. Sans extrait pertinent, le modèle n'est pas appelé du tout et la réponse est un aveu d'ignorance. Les pages citées viennent des extraits, jamais d'une analyse du texte produit par le modèle. Le modèle lit plus d'extraits qu'on n'en cite : docs.chat.max-chunks pour ce qu'il reçoit, docs.chat.max-sources pour ce que le lecteur voit.

    Une question passe par la même file que les générations de rapport. Sur un serveur occupé, la réponse attend son tour.

    La détection de dérive¶

    À chaque poussée, un travail d'intégration continue compare les fichiers modifiés aux sources des pages :

    • une source qui est un fichier précis et qui change, alors que la page ne change pas, fait échouer le travail. On sait exactement quelle page relire ;
    • une source qui est un dossier est seulement signalée : elle couvre trop de code pour qu'un changement quelconque prouve quoi que ce soit.

    Le lot contrôlé est la poussée entière, et non le seul dernier commit. Sur main, la base est le commit d'avant la poussée, que GitHub transmet au flux dans github.event.before et que le travail passe au script par --before : GitHub ne lance le flux que pour la tête d'une poussée, si bien qu'une comparaison de la tête à son seul parent laisserait passer tout commit poussé au milieu d'un lot. Quand ce commit est nul (branche neuve) ou étranger à l'historique de la tête (poussée forcée), le script se replie sur le parent de la tête. Sur une branche de travail, la base est l'ancêtre commun avec main : toute la branche est relue à chaque poussée. Le script imprime la plage qu'il contrôle en première ligne.

    Deux échappatoires quand une page signalée reste juste : la modifier dans le même lot de commits, ou la nommer dans un message de commit du lot, celui qui touche la source ou n'importe quel autre de la plage. Le script imprime les lignes à coller, une par page :

    [doc-ok] docs/manuel/administrateur/https.md

    Une exemption ne vaut que pour la page qu'elle nomme ; les autres continuent de bloquer. Le marqueur ne compte qu'en début de ligne, sans quoi le commit qui documente l'échappatoire la déclencherait en la citant.

    Le même marqueur sans aucun chemin exempte tout le lot. C'est un dernier recours, pas l'usage courant : il rend le contrôle silencieux sur des pages que personne n'a relues.

    Une montée de version seule, la ligne VERSION du flux de CI et rien d'autre, n'est pas un changement : livrer reste un seul geste, et aucune page qui décrit le flux n'en devient fausse. Toute autre ligne du flux qui bouge en même temps rend la relecture due.

    Ce travail ne bloque pas la publication d'une version : une documentation en retard ne doit pas empêcher un correctif de partir. Ni publish-images ni tag-release ne l'attendent ; les sept suites de tests, elles, sont attendues. Il ne pourrait pas l'être sans dommage : il ne tourne pas sur un déclenchement manuel du flux, faute d'une poussée à laquelle comparer, et un travail sauté fait sauter tout ce qui l'attend.

    python scripts/docs/check_drift.py --base origin/main --head HEAD

    Le site de relecture¶

    bash scripts/docs/preview.sh          # aperçu sur http://127.0.0.1:8000
bash scripts/docs/preview.sh build    # construction dans .mkdocs-site

    MkDocs avec le thème Material, configuré dans docs/mkdocs.yml. Il sert à relire longuement, avec recherche plein texte et navigation, sans la liste blanche du site publié : il montre aussi le suivi et les rapports. L'application reste la voie normale de lecture.

    Les blocs de commandes sont rendus par pymdownx.superfences et non par le fenced_code que MkDocs active d'office : celui-ci ne reconnaît pas une clôture indentée sous un item de liste, et les procédures numérotées des manuels en sont pleines. Mal rendu, un bloc devient une portion de code en ligne qui commence par bash, sans retours à la ligne, et un administrateur qui la recopie lance une commande qui n'est pas celle du manuel. scripts/docs/test_rendu.py joue le rendu de chaque page avec les extensions déclarées et refuse toute portion de code en ligne qui commence par un nom de langage.

    Le site publié en ligne¶

    bash scripts/docs/preview.sh public   # construction dans .mkdocs-public-site

    Les manuels ne sont lisibles que dans l'application, donc illisibles le jour où rien ne démarre, qui est le jour où on en a besoin. Une copie statique des trois manuels est publiée en ligne, lisible sur un téléphone, serveur éteint, à un millier de kilomètres du support. Le manuel développeur y est entré le 27/10/2026, avec ses schémas HTML ; jusque-là il restait servi par l'application seulement, au motif qu'il décrit les faiblesses connues de la machine. Les rapports figés, les contrats et le suivi ne sortent pas.

    La liste blanche¶

    L'exclusion est structurelle, et non une liste de retraits. scripts/docs/build_public.py pose deux portes, toutes deux positives :

    • de la navigation de docs/mkdocs.yml, seules les sections nommées dans PUBLIC_SECTIONS sont retenues, et chacune de leurs pages doit commencer par un préfixe de PUBLIC_PREFIXES. Une page publiable qui désignerait developpeur/ ou ../notes.md arrête la construction ;
    • les pages retenues sont copiées dans un dossier d'étape, .mkdocs-public-src, qui est le docs_dir du site public. MkDocs publie tout ce qu'il trouve dans son docs_dir, inscrit à la navigation ou non : rien ne peut donc être publié sans avoir d'abord été copié. Les schémas HTML rangés à la racine d'un manuel publié (cycle-de-vie-acte.html, les moissonnages) sont copiés avec lui et servis tels quels, hors navigation, atteints par les liens des pages. Seul le dossier docs/manuel/assets/ traverse en bloc : il porte le K de Kauze, logo et favicon des deux sites, déclaré dans le theme de docs/mkdocs.yml.

    docs/mkdocs-public.yml hérite du site de relecture pour le thème et les extensions, et ne change que son identité et son docs_dir. Il ne porte pas de navigation : elle est dérivée de la liste blanche, ce qui évite deux ordres de lecture qui divergeraient. L'accueil du site publié est scripts/docs/accueil-public.md, hors de docs/manuel/ parce qu'il n'appartient à aucun manuel.

    Une page ajoutée à l'un des trois manuels est publiée dès qu'elle entre dans la navigation, un schéma HTML dès qu'il est posé à la racine du manuel. Un fichier à la racine de docs/, ou un dossier ajouté sous docs/, ne franchit aucune des deux portes.

    Ce qui l'atteste¶

    scripts/docs/test_publication.py vérifie la liste blanche, puis construit le site sur une copie du dépôt où cinq témoins ont été semés : une page et un schéma HTML sous docs/manuel/developpeur/, qui doivent sortir, page indexée et schéma servi tel quel ; un fichier et un schéma à la racine de docs/, et un dossier neuf sous docs/, qui ne doivent se retrouver ni dans le site ni dans search/search_index.json, dont aucun emplacement ne doit sortir des trois manuels publiés. Ces tests tournent dans le travail doc-drift, qui joue déjà pytest dans scripts/docs, et une seconde fois dans le flux de publication, juste avant la poussée.

    Le flux de publication¶

    .github/workflows/docs-publish.yml, à part du flux d'intégration continue. Il ne tourne que sur main, et seulement quand les manuels publiés ou l'outillage de publication changent, plus un déclenchement manuel : une publication de documentation qui tourne sur chaque branche de travail est du gonflement pur.

    Il joue les tests du filtre, construit le site, le dépose en artefact manuels-publics, puis le pousse vers un dépôt public dédié qui ne contient que le site. La liste blanche y devient physique, puisque seul ce qui est poussé existe, et la poussée est un commit orphelin forcé : aucun historique du dépôt privé ne suit.

    L'étape de poussée dort tant que la variable de dépôt DOCS_PUBLIC_REPO est vide. Sans elle, le flux construit, vérifie et dépose l'artefact, qu'on peut télécharger pour voir exactement ce qui partirait.

    Armer la publication¶

    Gestes humains, une seule fois. Le dépôt privé n'étant pas sur un plan payant, GitHub Pages n'y est pas disponible : c'est le dépôt public dédié qui sert le site.

    1. Créer le dépôt public, qui ne contiendra que le site construit :

      gh repo create zero-filtre/kauze-manuels --public \
    --description "Manuels utilisateur et administrateur de CAUSE"

    2. Créer un jeton d'accès personnel à portée fine, limité au seul dépôt zero-filtre/kauze-manuels, avec la permission Contents: read and write, puis le poser sur le dépôt privé avec la cible et le domaine :

      gh secret set DOCS_PUBLIC_TOKEN   --repo zero-filtre/cause --body '<jeton>'
gh variable set DOCS_PUBLIC_REPO   --repo zero-filtre/cause --body 'zero-filtre/kauze-manuels'
gh variable set DOCS_PUBLIC_DOMAIN --repo zero-filtre/cause --body 'manuels.kauze.tech'

      Un jeton expiré arrête la publication et rougit le flux ; le site déjà en ligne reste servi.

    3. Pointer le sous-domaine chez deSEC, en gardant le point final :

      curl -s -X POST https://desec.io/api/v1/domains/kauze.tech/rrsets/ \
     -H "Authorization: Token <jeton deSEC>" \
     -H "Content-Type: application/json" \
     -d '{"subname": "manuels", "type": "CNAME", "ttl": 3600,
          "records": ["zero-filtre.github.io."]}'

    4. Déclencher le flux, qui crée la branche gh-pages du dépôt public :

      gh workflow run docs-publish.yml --repo zero-filtre/cause --ref main

    5. Activer Pages sur le dépôt public, la branche devant exister d'abord. Le certificat du sous-domaine est délivré tout seul, en quelques minutes :

      gh api -X POST repos/zero-filtre/kauze-manuels/pages \
    -f 'source[branch]=gh-pages' -f 'source[path]=/'
gh api -X PUT repos/zero-filtre/kauze-manuels/pages \
    -f cname=manuels.kauze.tech -F https_enforced=true

    6. Vérifier les deux sens, ce qui doit répondre et ce qui doit manquer :

      curl -sI https://manuels.kauze.tech/ | head -1
curl -sI https://manuels.kauze.tech/administrateur/depannage.html | head -1
curl -sI https://manuels.kauze.tech/developpeur/index.html | head -1   # 404 attendu

    Pour retirer la publication : vider la variable DOCS_PUBLIC_REPO, supprimer l'enregistrement CNAME chez deSEC, et supprimer le dépôt public.

    Écrire une page¶

    Une page décrit ce que le logiciel fait, pas ce qu'on aimerait qu'il fasse. Quand le code a un défaut connu, la page le dit comme un fait, à sa place, sans le maquiller ni l'excuser. Les libellés d'interface sont cités tels qu'ils apparaissent à l'écran.

    Une page dit aussi ce qui est, pas ce qui est arrivé : quand une raison éclaire une règle, elle tient en une proposition subordonnée accrochée à cette règle. L'incident, la date et la panne qui ont produit la règle vivent dans l'historique du dépôt, pas dans le manuel, où ils noient la règle et bruitent l'index de recherche.

    Ajouter une page, c'est l'ajouter aussi à la navigation de docs/mkdocs.yml et au sommaire de l'index de son manuel.

    Le patron des pages administrateur¶

    Une page du manuel administrateur n'explique pas, elle fait faire. Chaque procédure porte un titre de niveau 2 et exactement trois blocs de niveau 3, dans cet ordre :

    ### Ce qu'il faut faire      etapes numerotees, imperatif, une commande par etape
### Vérifier                 une ou deux commandes, et ce que la reponse doit montrer
### Si ça coince             un lien vers depannage.md

    Pas de section « Pourquoi », pas de « Comment ça marche en interne », pas de récit : phrases courtes, impératif, deuxième personne. Les tableaux de référence restent, variables d'environnement, codes de sortie, symptômes : c'est de la consultation, pas du récit. Tout le reste, le pourquoi d'un réglage, le fonctionnement interne d'un script, le détail d'un arbitrage, vit dans le manuel développeur.
