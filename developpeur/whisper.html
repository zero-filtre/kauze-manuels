    Services de transcription¶

    Deux moteurs, une seule interface. Le médecin a tranché le 11/10/2026 : Qwen3-ASR pour les actes dictés, où le lexique du praticien domine, Whisper pour les actes interactifs, où l'accent et l'articulation du patient pèsent davantage. Les deux servent la même route compatible OpenAI, chacun sur son port : le backend bascule d'un moteur à l'autre en changeant une URL, sans rien savoir du moteur qui répond.

    Service Port Moteur Démarre par défaut
    whisper 8999 faster-whisper large-v3 oui
    qwen-asr 8998 Qwen3-ASR-1.7B non, profil qwen

    Whisper¶

    Un serveur FastAPI qui expose faster-whisper avec une interface compatible OpenAI.

    Endpoints¶

    Méthode Chemin But
    GET / Informations sur le modèle chargé.
    GET /health Sonde utilisée par le healthcheck Docker.
    POST /v1/audio/transcriptions Transcription. Multipart avec file, plus model ignoré, language à fr par défaut, response_format parmi json, text et verbose_json, et temperature à zéro.

    La réponse au format json ne contient que la clé text. Le backend n'en lit rien d'autre.

    Côté backend, WhisperClientImpl se déclare comme le moteur de transcription nommé whisper : c'est la valeur attendue par les variables ASR_LIVE_PROVIDER et ASR_DICTATED_PROVIDER, qui choisissent le moteur de chaque piste, voir Configuration.

    Paramètres de décodage¶

    Le modèle est chargé au démarrage, d'après WHISPER_MODEL, avec détection automatique du matériel et du type de calcul. Le décodage utilise une recherche en faisceau de largeur cinq, un filtre d'activité vocale avec un seuil de 0,5, une parole minimale de 250 millisecondes et un silence minimal de 2 secondes, sans conditionnement sur le texte précédent.

    Ces valeurs ont un effet direct sur la qualité des portions courtes. Toute modification doit être mesurée avec le banc d'essai de transcription, pas jugée à l'oreille sur un fichier.

    Versions épinglées¶

    Les deux listes de dépendances épinglent leurs versions avec ==, sans quoi une reconstruction installe en silence un autre jeu de versions et le banc de performance mesuré avant la livraison ne dit plus rien de ce qui tourne sur la machine.

    Paquet Version Où
    faster-whisper 1.2.1 Dockerfile
    ctranslate2 4.8.3 Dockerfile
    fastapi 0.143.0 Dockerfile et requirements-test.txt
    uvicorn[standard] 0.54.0 Dockerfile
    python-multipart 0.0.32 Dockerfile et requirements-test.txt
    pytest 9.1.1 requirements-test.txt
    pytest-asyncio 1.4.0 requirements-test.txt
    httpx 0.28.1 requirements-test.txt

    ctranslate2 est épinglée explicitement bien qu'elle ne soit qu'une dépendance de faster-whisper : c'est elle qui se lie à CUDA, donc elle qui décide si l'image démarre sur le GPU. Ses roues officielles 4.8.3 sont compilées contre CUDA 12.8 avec WITH_CUDNN=OFF, ce qui correspond à la base nvidia/cuda:12.8.1-cudnn-runtime-ubuntu22.04. Toute montée de version de ctranslate2 doit être vérifiée contre la base : si une version future exige CUDA 13 ou cuDNN 10, c'est la base qu'il faut changer d'abord, pas l'épingle.

    fastapi et python-multipart portent la même version dans les deux fichiers : le serveur testé en intégration continue doit être celui qui tourne dans l'image.

    httpx reste en 0.28.1, la dernière version stable ; la série 1.0 n'existe qu'en préversions et une épingle de préversion n'a pas sa place dans une livraison.

    Ce que ces épingles ne couvrent pas. Elles tiennent les paquets que nous nommons, pas l'image. Les dépendances indirectes (onnxruntime, av, tokenizers, huggingface-hub, numpy, starlette) peuvent encore glisser d'une reconstruction à l'autre ; les figer demanderait un fichier de verrouillage, et ce n'est pas fait. L'étiquette de base nvidia/cuda:12.8.1-cudnn-runtime-ubuntu22.04 est mobile et n'est pas épinglée par condensé, et apt-get install python3-pip prend le pip du moment. Une reconstruction n'est donc pas identique à la précédente : l'image livrée est celle qu'on a mesurée, pas celle qu'on saurait refaire au bit près.

    Construction et tests¶

    Les dépendances d'exécution sont installées dans l'image, à partir de la base CUDA. Il n'existe pas de requirements.txt : ne pas le documenter ni s'y fier. Les tests utilisent requirements-test.txt et un modèle simulé.

    cd scripts/faster-whisper
pip install -r requirements-test.txt
pytest -v

    Le cache des modèles Hugging Face pointe dans ~/.cause/whisper. En production, le mode hors ligne est actif par défaut : le script d'installation le lève le temps du premier démarrage.

    Qwen3-ASR¶

    scripts/qwen-asr/ reprend le pli de scripts/faster-whisper/ : un serveur FastAPI, la même route, le même port dédié publié sur l'hôte, le même montage de ~/.cause, les mêmes variables d'exploitation (CAUSE_LOG_DIR, HF_HUB_OFFLINE, LOG_LEVEL). Le journal part dans ~/.cause/logs/cause-qwen-asr-<date>.log, préfixé [QWEN-ASR].

    Endpoints¶

    Méthode Chemin But
    GET / Modèle chargé, carte utilisée, type de calcul.
    GET /health Sonde utilisée par le healthcheck Docker.
    POST /v1/audio/transcriptions Transcription. Multipart avec file, plus model ignoré, language, response_format parmi json, text et verbose_json, temperature ignoré, et prompt facultatif.

    Deux différences de forme avec Whisper, et elles sont dans le serveur, pas dans le contrat :

    • language accepte un code ISO (fr, fr-FR, pt_BR) comme un nom (French). Qwen3-ASR n'accepte que des noms de langue en clair, parmi les trente qu'il connaît ; la table de conversion vit dans le serveur. auto ou une valeur vide laissent le moteur détecter la langue. Une langue hors modèle est refusée en 400 plutôt que transcrite dans une autre.
    • prompt devient le contexte de biaisage du moteur, le context de l'API Qwen. C'est le champ par lequel un lexique métier peut être poussé au moteur sans changer le contrat OpenAI. Whisper ignore ce champ, Qwen s'en sert.

    temperature est accepté et ignoré : Qwen3-ASR décode en greedy.

    La réponse au format json ne contient que la clé text, comme Whisper. En verbose_json, la durée est lue dans l'en-tête du fichier et non rendue par le moteur, et il n'y a qu'un segment : les horodatages de Qwen3-ASR demandent un second modèle (Qwen3-ForcedAligner-0.6B) que nous ne chargeons pas. Une durée illisible ne coûte pas la transcription, elle rend null.

    Côté backend¶

    QwenClientImpl se déclare comme le moteur de transcription nommé qwen : c'est la valeur attendue par ASR_DICTATED_PROVIDER, voir Configuration. Il poste le même multipart que WhisperClientImpl et ne lit que la clé text de la réponse ; une réponse sans cette clé est une erreur, pas une transcription vide.

    Variable Défaut Rôle
    ASR_DICTATED_PROVIDER whisper Moteur de la piste dictée, qwen pour la confier à Qwen3-ASR.
    ASR_QWEN_URL vide Route du service. Dans le compose : http://qwen-asr:8998/v1/audio/transcriptions.

    Le préfixe ASR_ n'est pas décoratif : scripts/setup.sh ne recopie vers le conteneur backend que les variables dont le préfixe figure dans BACKEND_ENV_PREFIXES, où ASR_ est déclaré et QWEN_ ne l'est pas. Une variable nommée QWEN_ASR_URL serait lue par Spring en développement et resterait muette dans le conteneur livré. Les variables QWEN_* (modèle, carte, fenêtre audio) règlent le service Python et non le backend : docker compose les lit sur l'hôte.

    Poser ces deux variables et redémarrer le backend suffit à basculer la dictée sur Qwen : aucune image à reconstruire, aucun changement de code. Les reposer à whisper ramène l'état précédent.

    Quand le moteur est nommé mais au repos¶

    Sans ASR_QWEN_URL, le bean reste dans le contexte et se déclare non configuré : le serveur démarre normalement, la piste directe transcrit, et seule la piste qui nomme qwen reçoit une AsrEngineUnavailableException, soit un 503 de titre ASR Engine Unavailable, dont le détail nomme le moteur demandé et la piste, doublé des propriétés asrProvider et asrTrack. Un administrateur à distance lit donc sur la réponse quel moteur manquait, pour quelle piste, et que Whisper n'est pas en cause.

    Avec une URL posée mais le service arrêté (profil qwen non activé), l'échec est une erreur de connexion dont le message nomme le moteur qwen et son URL. Dans les deux cas l'appel refuse au lieu d'attendre, et aucun rapport vide n'est produit.

    Pourquoi le paquet qwen-asr et non transformers seul¶

    Les poids publiés sur Qwen/Qwen3-ASR-1.7B portent des noms préfixés thinker.. La série transformers 4.57 ne connaît pas du tout l'architecture qwen3_asr ; la série 5.x en a une implémentation propre, dont les noms de poids ne sont pas ceux du point de contrôle publié : le chargement laisse toutes les clés inattendues, le modèle démarre avec des poids tirés au hasard et transcrit n'importe quoi, sans autre avertissement qu'un rapport de chargement.

    Le paquet officiel qwen-asr porte le code du modèle et exige transformers==4.57.6 : c'est la seule voie transformers qui fonctionne avec les poids tels qu'ils sont publiés. Il est installé avec --no-deps, parce que sa liste de dépendances tire gradio, flask, sox et pytz, une interface de démonstration dont un serveur de production n'a que faire ; ses dépendances d'exécution réelles sont épinglées à la main juste au-dessus. Son autre moteur, vLLM, est écarté : l'image vllm/vllm-openai pèse 27,8 Go dépliée, contre 6,5 Go pour celle-ci.

    Le découpage des longs fichiers est celui du paquet : une passe jusqu'à 1200 secondes d'audio, puis des morceaux enchaînés avec report du texte précédent.

    Versions épinglées¶

    Paquet Version Pourquoi
    qwen-asr 0.0.6 Le code du modèle. Installé --no-deps.
    transformers 4.57.6 Exigée par qwen-asr. La 5.x ne charge pas ces poids.
    torch 2.14.1 Roues PyPI, qui embarquent leur runtime CUDA 13.
    accelerate 1.12.0 Épingle de qwen-asr (device_map).
    librosa 1.0.0 Lecture et rééchantillonnage de l'audio.
    soundfile 0.14.0 Lecture de l'audio, et la durée de l'en-tête.
    nagisa 0.2.11 Épingle de qwen-asr, importée au chargement.
    soynlp 0.0.493 Épingle de qwen-asr, importée au chargement.
    qwen-omni-utils 0.0.9 Épingle de qwen-asr.
    fastapi, uvicorn[standard], python-multipart 0.143.0, 0.54.0, 0.0.32 Mêmes versions que le serveur Whisper.

    La base n'est pas une image CUDA mais python:3.12-slim : les roues torch de PyPI embarquent leur propre runtime CUDA, qu'une base CUDA ne ferait que dupliquer. En contrepartie, les deux variables NVIDIA_VISIBLE_DEVICES et NVIDIA_DRIVER_CAPABILITIES que les images NVIDIA posent d'office sont déclarées dans le Dockerfile : sans elles, le runtime de conteneur n'injecte pas les bibliothèques du pilote et la carte reste invisible.

    gcc est installé dans l'image et n'y est pas un reste de compilation : torch 2.14 implémente en Triton l'opérateur bmm_outer_product qu'appelle l'encodeur audio, et Triton compile son lanceur à la première transcription. Sans compilateur C, le serveur démarre, répond /health et rend une erreur 500 sur la première vraie requête. Le cache de Triton est posé sous ~/.cause/qwen-asr/triton pour que cette compilation ne soit pas refaite à chaque redémarrage du conteneur.

    Comme pour Whisper, ces épingles ne tiennent que les paquets nommés. Les dépendances indirectes (numpy, numba, scipy, soxr, tokenizers, huggingface-hub) peuvent encore glisser d'une reconstruction à l'autre, et l'étiquette de base n'est pas épinglée par condensé.

    Poids de l'image¶

    Mesuré : 3,40 Go en archive docker save, celle qui voyage sur le disque de livraison, contre 3,03 Go pour l'image Whisper et 8,8 Go pour vllm/vllm-openai. Dépliée sur la machine, elle pose 6,9 Go de fichiers, dont 6,5 Go de paquets Python : 3,4 Go de bibliothèques NVIDIA, 1,2 Go de torch, 0,9 Go de Triton, et moins de 1 Go pour tout le reste. docker images en annonce 10,5 Go, qui est la somme de ses couches et non ce qu'elle pose, contre 8,1 Go annoncés de la même façon pour Whisper.

    Ce qui resterait à tailler est modeste et risqué : NCCL, cuSPARSELt et NVSHMEM, qui ne servent qu'au multi-carte et aux noyaux creux, pèsent 0,5 Go dépliés, mais les écarter suppose d'installer torch lui-même en --no-deps et de revérifier la liste à chaque montée de version. Triton, lui, n'est pas retirable : c'est lui qui porte l'opérateur ci-dessus.

    VRAM, et la place qui reste¶

    Mesuré sur une RTX 5060 Ti, le modèle en bfloat16 chargé sur une seule carte, occupation relevée à nvidia-smi pendant la requête :

    Audio soumis VRAM au pic
    modèle chargé, au repos 4,9 Go
    portion de 30 s 5,0 Go
    2 min 5,4 Go
    5 min 9,4 Go
    15 min, fenêtre par défaut 12,1 Go
    15 min, fenêtre bornée à 2 min 6,5 Go
    15 min, fenêtre bornée à 1 min 5,2 Go

    Les poids ne pèsent que 3,80 Gio pour 2,04 milliards de paramètres : c'est l'encodeur audio qui fait la facture, et elle suit la durée soumise d'une traite. D'où QWEN_MAX_SECONDS, à 120 par défaut, qui borne cette fenêtre : le découpage reste celui du paquet, qui coupe sur les silences et reporte le texte déjà transcrit d'un morceau au suivant. La valeur 0 rend la main au paquet et sa fenêtre de vingt minutes, et une minute suffit à ramener un quart d'heure de dictée sous les 5,2 Go. Une couture à connaître : le paquet recolle les morceaux sans séparateur, d'où des phrases accolées à chaque jointure, que la rédaction en aval reponctue.

    La machine du CHU a deux cartes de 16311 Mio, et la pile y monte à 26,5 Go au pic sous charge, cumulé sur les deux cartes. Le modèle de rédaction s'étale sur les deux, Whisper occupe la première : au repos, la carte la moins chargée n'a qu'environ 6,4 Go de libre, et moins sous charge. Qwen3-ASR ne tient donc pas d'office : c'est pourquoi le service ne démarre pas avec les autres, et pourquoi QWEN_DEVICE doit nommer explicitement la carte (QWEN_DEVICE=cuda:1) au lieu de laisser auto prendre la première. Avec la fenêtre à une minute, le moteur demande 5,2 Go quelle que soit la longueur de la dictée : c'est la seule configuration qui passerait aujourd'hui, et sans marge. L'alternative est de libérer une carte, en ramenant la rédaction sur une seule, ou d'attendre la montée en VRAM.

    docker compose --profile qwen up -d qwen-asr

    Son image voyage sur le disque de livraison comme les deux autres et le script la charge, ses 4,4 Go de poids sont posés dans ~/.cause/qwen-asr/hub par la mise en place, mais le compose du client le déclare derrière le profil qwen : docker compose up -d ne le démarre pas. Le réveiller ne demande donc aucun téléchargement, seulement la commande ci-dessus. Démarré, le moteur ne transcrit encore rien : c'est ASR_DICTATED_PROVIDER qui lui envoie la dictée.

    Trois autres variables règlent la consommation : QWEN_DTYPE (bfloat16 par défaut), QWEN_BATCH_SIZE (1 par défaut, pour éviter de payer un lot en mémoire) et QWEN_MAX_NEW_TOKENS (4096, à monter pour un très long dicté).

    Construction et tests¶

    cd scripts/qwen-asr
pip install -r requirements-test.txt
pytest -v

    Les tests simulent le moteur, torch et le lecteur audio : ils ne demandent ni carte graphique, ni réseau, ni les 4,4 Go du modèle. Le travail test-transcription les joue à chaque poussée, avec ceux de Whisper, les deux suites partageant un seul exécuteur.

    Le cache des modèles Hugging Face pointe dans ~/.cause/qwen-asr, et le mode hors ligne est actif par défaut, comme pour Whisper : le premier démarrage d'une machine neuve demande de le lever le temps du téléchargement.
