    Configuration¶

    Les propriétés vivent dans application.yml, avec une surcouche de production. Chaque domaine a sa classe de propriétés typées, sauf quelques valeurs lues par annotation directe.

    Domaine Clés principales Classe
    Serveur et authentification server.port, auth.jwt-secret, auth.token-expiration-hours lues par annotation dans le service d'authentification
    Envoi de fichiers spring.servlet.multipart.* Spring
    Embedding spring.ai.embedding.transformer.* Spring AI
    Clients HTTP http-client.connect-timeout, read-timeout, write-timeout HttpClientConfig
    Whisper medical-record.whisper.endpoint, model, language WhisperProperties
    Moteur de transcription par piste asr.live-provider, asr.dictated-provider AsrProperties, AsrEngineFactory
    Mutex GPU medical-record.gpu-mutex-enabled GpuLockService
    Stockage medical-record.storage.*, dont les dossiers de données et les purges annotations dans les repositories
    Parcours medical-record.recording-flow.golden-rules-consultation-threshold ConsultationService
    Verrou medical-record.visibility-lock.timeout, expiry-check-interval VisibilityLockService, LockExpiryTask
    Portions medical-record.segments.* AudioSegmentService
    Seuil de transcription transcription.threshold.min-length, min-word-count TranscriptionThresholdProperties
    Édition de portion segment-editing.enabled SegmentEditingProperties
    Moissonnage asr-harvest.* AsrHarvestProperties
    Génération report.generation.segment-check-interval-seconds, max-wait-time-seconds, workers ReportGenerationProperties
    Rédactions orphelines report.generation.stale-check-interval, stale-grace-seconds StaleGenerationTask

    Corpus d'entraînement medical-record.storage.training-corpus-dir, training-corpus-enabled (TRAINING_CORPUS_ENABLED, vrai par défaut) TrainingCorpusStore

    Glossaire glossary.* GlossaryProperties

    Les profils¶

    Le backend lit application.yml puis, en production, la surcouche application-prod.yml activée par SPRING_PROFILES_ACTIVE=prod dans le docker-compose. En production :

    • le port est 8090 ;
    • Swagger et la documentation OpenAPI sont désactivés ;
    • l'endpoint /actuator/health ne renvoie que l'état global, sans détail ;
    • les logs sont écrits dans des fichiers sous ~/.cause/logs/.

    Comment une variable arrive dans le conteneur¶

    Deux chemins, et ils ne se valent pas.

    L'environnement de la machine. Le script d'installation copie dans .env.backend chaque variable de l'environnement dont le nom commence par un préfixe connu : SPRING_, SERVER_, MANAGEMENT_, LOGGING_, SPRINGDOC_, AUTH_, HTTP_CLIENT_, TASK_, WHISPER_, ASR_, MEDICAL_RECORD_, TRANSCRIPTION_, REPORT_, LLM_, OLLAMA_, AIRLLM_, OPENAI_, SMOOTHING_, ENRICHMENT_, REMONTEE_, TRAINING_CORPUS_. C'est le chemin des machines de développement et de l'intégration continue, où l'environnement est déjà la source de vérité. Sur un serveur, il demande de modifier /etc/environment puis de relancer le script.

    Le fichier de réglages de l'administrateur, ~/.cause/.env.backend.overrides, lu en dernier, donc il l'emporte. Aucun nom n'y est interdit, et il ne filtre rien : c'est le seul chemin pour GLOSSARY_, SEGMENT_EDITING_, LECTURE_ et CAUSE_, dont le préfixe n'est pas dans la liste ci-dessus. Le script n'y écrit jamais rien.

    La règle de partage entre les deux fichiers générés est simple : .env.backend porte ce que nous avons généré, à l'installation ou à la gravure ; .env.backend.overrides porte ce que l'administrateur décide d'y mettre à la main ensuite. Les deux portent des secrets possibles, donc aucune sauvegarde ne les emporte, et .env.ghcr, partagé avec l'éditeur, est maintenu en 600. Les identifiants du stockage ne doivent jamais être écrits dans .env.backend, que le script réécrit à chaque passage.

    Sur une machine de développement, ces fichiers sont dans le dépôt, à côté du compose qui les lit : chacun vit toujours auprès du compose qui fait foi.

    Le docker-compose, enfin, fixe lui-même le câblage entre les services, et ces valeurs passent avant celles des deux fichiers : SPRING_PROFILES_ACTIVE, WHISPER_URL, MEDICAL_RECORD_WHISPER_ENDPOINT, OLLAMA_URL, OLLAMA_MODEL et ENRICHMENT_ENABLED.

    Moteurs de transcription¶

    Le moteur n'est pas le même selon qui parle : Whisper encaisse mieux l'accent et la mauvaise articulation des patients, un moteur plus précis sur le lexique médical sert mieux la dictée du praticien. Le choix se fait donc par piste, pas par type d'acte, et s'externalise par deux variables, ASR_LIVE_PROVIDER pour le direct et ASR_DICTATED_PROVIDER pour la dictée. Les actes sans piste live (exam, surgery) reçoivent de fait le moteur de la dictée.

    Un moteur apporte aussi son adresse : ASR_QWEN_URL pour Qwen3-ASR, vide par défaut. Le préfixe ASR_ n'est pas décoratif, c'est lui qui fait franchir la porte du conteneur par le chemin de l'environnement : scripts/setup.sh ne recopie dans .env.backend que les variables dont le préfixe figure dans BACKEND_ENV_PREFIXES. Une variable nommée QWEN_* serait lue en développement et muette en production, à moins d'être écrite dans .env.backend.overrides, qui ne filtre rien.

    Les deux défauts valent whisper, donc une installation qui ne pose rien se comporte comme avant l'arrivée d'un second moteur. Reposer les deux variables à whisper et redémarrer ramène ce comportement : c'est le filet de l'installation hospitalière, et aucune image n'est à reconstruire.

    Côté code, AsrEngine est l'interface d'un moteur, qui porte son nom, dit s'il est configuré et transcrit ; chaque implémentation est un bean, AsrEngineFactory les indexe par nom et TranscriptionService lui demande le moteur de la piste reçue. Deux propriétés tiennent par les tests (AsrEngineFactoryTest, asr-routing.feature, AsrEngineStartupTest) :

    • une variable absente, vide ou dans une autre casse ne fait pas dérailler le choix, elle retombe sur whisper ;
    • une variable qui nomme un moteur que le serveur ne sert pas, ou un moteur sans URL, ne fait pas échouer le démarrage : elle lève une AsrEngineUnavailableException au moment où la piste demande son moteur, ce qui met la portion en échec et laisse l'autre piste intacte.

    Pièges connus¶

    • La licence machine n'a aucune propriété, les variables d'environnement primant sur les fichiers de profil, y compris application-prod.yml : une clé licence.enabled se débrancherait en une ligne, et des chemins de sources configurables feraient lire une identité fabriquée. Tout est compilé dans LicenceConfig, et LicenceConfigTest vérifie qu'aucune clé licence ne réapparaît dans les fichiers de configuration. Le bean s'efface sous le profil test, dont la configuration de remplacement vit dans les sources de test et n'est jamais livrée. La durée de la fenêtre de grâce, soixante-douze heures, est compilée pour la même raison.

    • La durée maximale de consultation est déclarée dans les propriétés de portions mais n'est appliquée nulle part. Ne pas la documenter comme une limite effective.

    • Le défaut Java du mutex GPU est l'inverse du défaut du fichier. C'est le fichier qui gagne.
    • Le secret de jeton est versionné dans le fichier de configuration, sans surcouche de production. Toute installation doit le remplacer par variable d'environnement, à une valeur longue, aléatoire et propre à l'établissement : c'est elle qui signe les sessions, et deux serveurs qui la partagent acceptent les jetons l'un de l'autre.
    • Le profil test a son propre fichier : dossiers de données isolés sous target, édition de portion activée, moissonnage désactivé, workers non démarrés, remontée éteinte.
    • La remontée est active mais n'a pas de clés par défaut, et c'est une règle, pas un oubli. Le stockage est celui de l'éditeur : son seau, sa racine et sa région sont les mêmes partout, donc ce sont des défauts versionnés, posés aux deux mêmes endroits, RemonteeProperties et application.yml. Les deux clés, elles, sont des secrets et n'ont aucune valeur dans le dépôt ; l'avertissement unique d'une remontée incomplète est le rappel qu'il faut les poser. Les tests signent contre des identifiants manifestement faux et un faux point de terminaison local, jamais contre le réseau : le profil test efface les trois valeurs versionnées pour qu'aucun test ne puisse joindre le vrai seau.
    • Le bloc task de la racine est l'espace de noms du projet, lu par CauseApplication pour l'exécuteur @Async. Le vivier du planificateur @Scheduled est ailleurs, spring.task.scheduling.pool.size : une taille posée dans le bloc racine serait ignorée sans que rien ne le dise.

    Les valeurs d'exploitation et leur effet côté serveur sont dans Configuration du manuel administrateur.
